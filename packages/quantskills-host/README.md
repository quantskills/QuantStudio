# @deepseek-ai/dsh-quantskills-host

English | [中文](README.zh.md)

Catalog asset ids accept lowercase letters, digits, hyphens, and underscores while keeping the exact `skill-` or `agent-` prefix and official repository match. The envelope, snapshot, taxonomy, and response bounds remain strict, but each asset row is admitted independently: a malformed, substituted, duplicated, or otherwise invalid row is omitted instead of making every valid asset unavailable.

Trusted Host projection, immutable official installer, and private local-authoring publisher for QuantSkills assets. `QuantSkillsHostGateway` publishes cancellable Typert Remotes under `quantSkills/catalog`, `quantSkills/catalogSyncStatus`, `quantSkills/list`, `quantSkills/applicationUpdateStatus`, `quantSkills/applicationUpdateCheck`, `quantSkills/applicationUpdateStart`, `quantSkills/assetReadme`, `quantSkills/install`, and `quantSkills/agentTemplate`. The Client assembly mounts those generated methods through [`api-remotes`](../../api/remotes/README.md). Same-process methods resolve one exact registry-visible installed Skill and publish a validated local draft; they reject absent versions, kind mismatches, and paths outside the authorized draft root.

`catalog` fetches only `https://raw.githubusercontent.com/quantskills/quantskills/main/site/catalog.json` or the same path at an exact 40-hex catalog-repository commit. It bounds the complete response, validates the snapshot id and every approved asset, excludes non-approved rows, and accepts only an exact `https://github.com/quantskills/<asset-id>` repository whose 40-hex commit and root declaration agree with its `skill` or `agent` kind. Its Client-safe snapshot includes the publication's dynamically sorted bilingual category and subcategory taxonomy plus summaries, description, health, validation level, dependencies, and stable localized display metadata. A published Chinese title wins; otherwise the Host deterministically derives a concise Chinese name from the asset id and Chinese summary, records its source, and retains the English name, aliases, and original asset id for search. The result is tied to the validated asset id and commit and never requires a model or render-time request. `list` additionally reads a Chinese H1 from each exact installed declaration, allowing the Client to prefer that declaration title only for the matching commit. Browser code does not need a second catalog fetch or a hard-coded category count. A fully validated response and its bounded entity tag remain in process memory. Later Client reads return that trusted snapshot immediately while the Host conditionally revalidates it with `If-None-Match` in the background; a `304` is accepted only when the validated cache exists, and a failed revalidation does not erase it. When `catalogEventsUrl` is configured, the Host maintains one outbound SSE connection and treats each accepted catalog event only as a hint to re-fetch this trusted URL; the relay can never supply catalog content or install source. The snapshot and `catalogSyncStatus` expose connection state, and the Host emits catalog and status events for Clients. Without a relay the advertised automatic-check delay, which defaults to five minutes, remains the fallback.

`assetReadme` serves the repository's root `README.md` only after revalidating the caller's observed catalog snapshot, approved asset id, and exact commit. It fetches the corresponding official raw GitHub URL on demand, rejects redirects and mismatched response URLs, enforces a separate timeout and complete UTF-8 byte limit, and never substitutes another branch or documentation file. A missing or invalid README fails only the detail request; it cannot change catalog approval or installation state.

`install` re-fetches the catalog and requires the caller's observed snapshot id and commit to match before starting Git. For an Agent it installs the union of the approved catalog dependencies and the standard `AGENTS.md` dependencies; every declared dependency must resolve to an approved Skill in the same snapshot and exact commit. It rejects cycles, absent dependencies, and Agent-to-Agent dependencies before publishing the template. Git runs through `ctx.subprocess` with argv only, no credential-shaped ambient environment, no system or global Git config, disabled prompting, an empty hook template, HTTPS as the only transport, and LF checkout independent of the host platform. The primary GitHub asset fetch has a configurable timeout that defaults to ten seconds; a timeout or Git failure switches the same origin to the matching Gitee repository and retries the exact catalog commit. Caller cancellation stops the complete installation instead of starting the fallback. The Host then checks out the exact commit, rejects symlinks, gitlinks, submodules, unsafe or colliding paths, and complete-tree limit violations, and verifies every checked-out file against its Git blob id.

Application updates are fully manual. `applicationUpdateCheck` is the only operation that queries the fixed official application repository and `main`; it compares commits without cloning or installing. If it reports `available`, the Client must obtain a second user confirmation before calling `applicationUpdateStart`. Preparation then clones into managed staging, installs the locked dependencies, runs source and isolated startup verification, and records a validated `pending` version for the stable launcher. Host initialization never performs this check, and a preparation failure cannot replace the running version or modify user data.

Accepted official source is published atomically under `<DSH_HOME>/quantskills/versions/<asset-id>/<commit>/source`; validated local authoring is published under `<DSH_HOME>/quantskills/authored/<asset-id>/<commit>/source`. Both stores use the same safe-tree validation, local Git snapshot, atomic publication, and private manifest format. Manifests record `origin: "catalog" | "local-authoring"`, identity, declaration, tree digest, complete size, and publication time. `list` reads only those manifests, so browser cache and Client state cannot create installed truth. Official installation still requires catalog provenance; local authoring instead rejects any id that conflicts with an official asset and never modifies or pushes a source repository. A Skill declaration must parse as a standard DSH Skill. Its name may equal the asset id or remove one leading `skill-` repository prefix; no other alias is accepted. The package's `quantskills-host` provider exposes the declaration name through `ctx.skills.list()` and `ctx.skills.get()` with the newest committed immutable source directory as `resourceBase`. An Agent declaration must use the standard root `AGENTS.md`, have the asset id as its name, and reference only exact installed Skill dependencies. `agentTemplate` exposes its bounded instruction body and dependency ids for explicit import, never as a Skill registry entry.

During declaration parsing the Host independently recognizes the first fenced `json qsh-form` block as optional version-one parameter metadata. It accepts an optional task, at most twelve `text`, `textarea`, `select`, `date`, or `number` fields, defaults, fixed select options, and one `prompt_template`. Only declared field names plus the reserved `task` and `attachments` variables may occur in the controlled Mustache template. Before strict validation, a deterministic compatibility adapter converts only canonical, finite JSON-number strings used as `number` field defaults and reports each conversion to the Client. Unsupported tags, malformed JSON, ambiguous values, invalid fields, and undeclared variables produce an `invalid` form result instead of rejecting installation or changing the declaration body. The adapter does not call a model and never escapes, rewrites, or removes upstream Skill or Agent text; Session composition registers that complete text through the system-prompt literal channel.

The Loader configuration controls the official catalog ref, optional event-relay URL and reconnect delay, catalog, README, and primary GitHub asset-fetch timeouts, automatic-check delay, catalog, README, and Git output bounds, Git executable and termination grace, and file-count, aggregate-byte, per-file, depth, and path-byte limits. The configured catalog URL still has to match the official URL grammar. The event relay must use HTTPS, except for loopback HTTP during local development, and must return a non-redirected `text/event-stream`; neither setting can widen repository ownership or installation transport policy.

## Model Experience

Indirectly, through existing Skill consumers that load the exact committed declaration and log rendered instructions or tool results; installation and form parsing themselves add no model input. A `qsh-form` fence remains part of the original declaration when that declaration is later loaded.

#### KV Cache effect

None until an installed Skill is selected. Its body then changes the same model-facing prefix as any other DSH Skill.

## Known Limitations and Deferred Work

- **Agent templates require explicit import** — installation validates and exposes `AGENTS.md`, but a user-owned editable Agent definition is created only when the Client imports that template.
- **No unattended Skill installation** — automatic checks only refresh the approved catalog projection. Installing a newer Skill remains an explicit user action because the global provider selects the newest committed version for ordinary consumers, while exact-version Sessions resolve their logged version directly. Application-version checks and preparation are separately user initiated. Explicit Skill rollback, referenced-version-aware removal, and garbage collection are deferred; deployments must retain every Skill version referenced by a Session log.
- **Catalog authenticity follows the official HTTPS publication** — the package validates source, schema, snapshot syntax, and asset provenance but has no separately signed catalog envelope.
- **Real-time delivery needs an external relay** — GitHub cannot push directly into a local DSH process behind NAT. A GitHub webhook or Action must notify the configured outbound SSE relay; without that deployment the Host uses focus and interval revalidation.
